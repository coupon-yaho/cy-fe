어느 패널이 어디서 데이터를 가져오는가

프로토타입의 관리자 화면을 그대로 복제하고, 각 박스에 커서를 올리면 원천·수집 방식·주기·함정이 뜹니다. 우하단 버튼으로 전부 펼칠 수도 있습니다.

D2는 정합성을 맨 위에 두고, 그 아래를 Four Golden Signals로 재편했습니다. 각 구역에 색 배지가 붙습니다.
C정합성 과제 합격 판정 · 최상단 LLatency 성공/실패 분리 TTraffic RPS ≠ TPS EErrors 3계층 SSaturation 60 / 75 / 85%
읽는 법 — 패널 우상단 칩이 데이터 원천입니다. 칩만 훑어도 화면의 데이터 토폴로지가 보입니다.
  • REDIS 실시간 상태. 재고·대기열. 읽기만 하고 새 카운터를 만들지 않습니다
  • MICROMETER 앱 프로세스 안. 무손실·지연 0. 지표 집계의 기본값
  • MYSQL 이력·통계·측정 결과. 관측 전용 DataSource로 읽습니다
  • 인메모리 스냅샷 링버퍼 900(15분) + 발급 이벤트 링버퍼 200. 둘뿐입니다
  • KAFKA 로그 수집(전 버전) · v3 영속화. 지표 집계에는 쓰지 않습니다

순서 주의 — 파티션 6·concurrency 3이면 Stream 입력 순서가 발생 순서가 아닙니다. 정렬은 occurredAt + eventId.

D2 11·12번 · 정합성 — 화면 B · 데이터 A

정합성은 B의 D2 화면에 있지만 계산 규칙(4개 gap)은 A의 도메인입니다. 같은 JVM이라 HTTP를 타면 안 됩니다.

interface ConsistencySnapshotProvider {   // A 구현
    ConsistencySnapshot get(long couponId);
}                                          // B 주입

앱 N대에서는 batch가 계산해 Redis에 올리고 API는 읽기만 합니다.

🔴 1초마다 전체 COUNT 금지

관측 전용 DataSource는 커넥션 풀만 분리합니다. MySQL CPU·I/O는 공유이므로 300만 행 집계를 초당 돌리면 성능 측정이 오염됩니다.

실시간 1초  luaGap · activeDbGap
             Redis + coupon_stocks PK 단건 = O(1)

최종 검증  dbCounterGap · persistGap · overIssued
             부하 종료 + persist lag=0 + 신규 발급 없음

Redis와 DB를 동시에 못 읽으므로 redisObservedAt·dbObservedAt·collectionDurationMs를 함께 반환합니다.

파티션 6 양쪽 동일

처리량 때문이 아닙니다. persist는 총 10,000건이라 파티션 1개로도 1초면 소화합니다. 6인 이유는 ⓐ 파티션은 줄일 수 없고 ⓑ concurrency가 파티션 수를 못 넘고 ⓒ 3의 배수라 브로커 3대에 균등 분배되기 때문입니다.

키가 파티션 수보다 중요합니다

persist → couponCode, attempt → memberId, notify → memberId. 절대 campaignId를 키로 쓰지 마세요 — 부하 테스트가 단일 캠페인(#1 모카빈)이라 파티션이 몇 개든 전부 한 곳에 몰립니다.

알림 발송은 T-5분 측정 보호

오픈 순간(T-0)에 발송하면 오픈런 부하와 겹쳐 v1/v2/v3 비교가 오염됩니다. 스케줄러가 T-5분에 신청자 전원을 발행하고, T-30초 워밍업과도 분리하세요.

auto.offset.reset이 반대입니다

persist=earliest — 한 건도 놓치면 "영구 미영속 발급 = 위반". attempt=latest — 재기동 시 수십만 건을 따라잡으면 DB를 때립니다.

프로듀서를 2개로 분리

persist는 acks=all + 멱등성, attempt는 acks=0 + enable.idempotence=false + max.block.ms=0. 하나의 KafkaTemplate으로 묶으면 로그 전송 실패가 발급 예외로 올라옵니다.

kafkaCB는 persist에만

attempt는 fire-and-forget이라 실패를 삼킵니다. CB를 걸 대상이 아닙니다.

프로세스 경계

컨슈머는 batch JVM에 있고 대시보드 API는 api JVM에 있습니다. lag은 batch가 metrics:kafka:{group}에 1초마다 쓰고 api가 읽습니다. TTL 3초 + observedAt 필수.

놓치기 쉬운 것 9

0 · 프로세스 경계 가장 잘 놓침

api와 batch는 별도 JVM입니다. batch에서 나는 것(Kafka lag, 만료 전이, 배치 실행 이력)은 api의 인메모리·MeterRegistry로 절대 못 읽습니다. 전부 batch → Redis → api로 넘기거나 DB를 경유하세요.

1 · 관측 전용 DataSource

안 만들면 Hikari 10개 중 1개를 대시보드가 먹습니다. 10%이고, v1의 병목이 정확히 그 풀입니다. 측정 대상을 관측이 바꿉니다.

2 · /entry는 전 버전에 존재

대기열 OFF여도 Entry-Token은 발급하고 GETDEL로 검증합니다. "대기열 없음" ≠ "Entry-Token 없음".

3 · issue_attempts 검증 제외

acks=0이라 유실 가능한데 검증 대상에 넣으면 "정상 셋 0건" 합격이 원천 불가능해집니다.

4 · 대기열 OFF 전환 가드

관리자가 OFF를 눌러도 ZCARD queue > 0이면 거부하고 DRAINING으로. 안 하면 대기 중인 1,500명을 신규가 추월합니다.

5 · 회차마다 토픽 초기화

attempt 토픽 + issue_attempts를 매 측정 전 비웁니다. 잔여 백로그가 다음 회차 DB 부하로 넘어옵니다.

6 · Lettuce 지연은 기본 0

LatencyUtils가 classpath에 없어 내장 collector가 꺼져 있습니다(확인함). MicrometerCommandLatencyRecorder를 ClientResources에 명시 wiring해야 값이 들어옵니다.

7 · 알림 발송은 T-5분

오픈 순간(T-0)에 보내면 오픈런 부하와 겹쳐 v1/v2/v3 비교가 통째로 오염됩니다. T-30초 워밍업과도 분리하세요.

8 · Mock에 실패율을 주입

Mock 어댑터가 100% 성공하면 패널 22가 항상 100%, DLQ가 항상 0이라 아무것도 증명하지 못합니다. 설정으로 실패율을 넣어 재발송·DLQ가 시연에서 살아나게 하세요.

9 · 회원 검색은 부분 일치 불가

이메일·전화는 AES 암호문이라 LIKE가 안 되고 email_hash는 HMAC이라 완전 일치만 됩니다. "hong%"로 찾는 UI를 그리면 구현에서 막힙니다.
